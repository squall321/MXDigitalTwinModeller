## Walking skeleton (build FIRST, ~3-4 days)
The thinnest end-to-end vertical slice, buildable in ~3-4 days, that proves the whole spine before ANY breadth: a single MCP call `generate_phone("146.7x71.5x7.4 flat slab, one display pocket, 4 corner holes")` -> LLM/parser fills a minimal C# PhoneParameters{L,W,T,corner_r,pocket{depth,bezel},holes[]} -> GenerationService.CreateBaseSolid() emits the bbox via the EXACT proven idiom (RectangleProfile -> Body.ExtrudeProfile -> DesignBody.Create), then runs 2 stages only: S00 bbox + S04 display pocket (reuse AddPocket ModificationService.cs:2784) + S06 four holes (reuse AddHole) -> the live body lands in SessionContext.Body -> a kernel-truth oracle asserts (a) one closed solid, (b) Volume within tol of L*W*T minus pocket minus 4 cylinders, (c) face-count == expected, (d) ContainsPoint probe: a point inside the pocket void returns OUTSIDE-material and a point in a remaining wall returns INSIDE -> ValidationService asserts min-wall(pocket-floor-to-back) >= param.min_wall. Deliberately FLAT and axis-aligned so it reuses 100% of the planar-bound helpers with zero new geometry verbs; it proves spec->params->generate->validate->verified-solid-in-SC and the MCP generate/regenerate transport, deferring ONLY the curved shell (P2) and ID-stability (P3). Success = the oracle passes deterministically across 3 back-to-back regenerates with different L/W/T.

## FIRST GATE (P0)
P0 / the FromEmptyComposition gate, runnable in 3-4 days: in a WriteBlock harness, CreateBaseSolid() emits a flat bbox from EMPTY, then AddPocket + AddHolePattern(4) + AddBoss compose on that generated body. It PASSES iff the result is one closed solid AND measured Volume == analytic (bbox minus cuts) within 1e-7 m^3 AND face-count == predicted AND a 6-point ContainsPoint material-side probe matches prediction (pocket-void=outside, wall=inside, hole-axis=outside). This is the smallest thing that proves from-scratch generation is viable at all — it directly attacks the program's central unverified assumption (the 82% number was measured only on MODIFY-of-imported-axis-aligned-CAD, never on from-empty composition). It is deliberately FLAT so it needs zero new geometry verbs, isolating the 'can the tools compose from empty' question from the harder 'curved shell' question (deferred to P2).

## Parametric model
PhoneParameters lives as a single C# class (Models/ReverseEngineer/PhoneParameters.cs) held by SessionContext as a SIBLING of Body/Graph — exactly where the live DesignBody already lives, so there is ONE source of truth in one process with no Python<->SC divergence. It holds: overall dimensions {L,W,T}; corner_r; chamfer/edge profile; bezels {top,bottom,side}; display pocket {depth, bezel, corner_r}; camera island {pos, w, l, h, corner_r} + lens layout {count, diameters, centers}; ports {type, pos, w, h, on_face}; speaker grille {array origin, pitch, rows, cols, hole_d}; button recesses; antenna slits; mic/sensor pinholes; min_wall. Design-intent rules are encoded as a Validate() method + a DesignRules helper enforcing constraint RELATIONSHIPS (not just per-field bounds): bump_height < total_thickness, bezel >= min_wall, lens-to-island clearance, grille pitch > hole_d, pocket_depth < T - min_wall. The params are AUTHORITATIVE because generation is deterministic param->stage replay (no incremental geometry that drifts from params): every regenerate discards/rebuilds from params via the StagePipeline, so the body can never silently diverge. The ONE place geometry could outrun params — an MCP mod-tool edit on the live body — is reconciled NOT by the fragile geometry->params extractor inverse but by routing such edits through set_parameter (the edit updates the param, then regenerate replays), keeping params as the master. Persisted to/from JSON for presets and session restore.

## Tool reuse mapping
The 20 mod tools map directly onto generation stages on the SAME live body (zero STEP crossing): S00 bbox = the cutter idiom from AddPocket/AddBoss (ModificationService.cs:2834/2839 ExtrudeProfile->DesignBody.Create); S04 display pocket = AddPocket (2784); S05 camera island = AddBoss (998, cylinder today; P4 adds rounded-rect plateau); S06 lens holes = AddHole (1111) / AddHolePattern (2522); S07 ports = AddSlit (2685); S08 grille = AddHolePattern (Grid mode); S09 buttons = AddPocket; S10 antenna = AddSlit; S11 mic/sensor = AddHole; S12 = AddChamfer/RoundEdges; incremental edits = ChangeHole/Boss/Wall/Fillet + Move/Rotate/Mirror/Remove. The MCP server (McpServer + ApiThreadMarshaller + SessionContext, kernel-agnostic transport) is reused as-is and gains tools nearly free. NEW tools/meta-tools needed: generate_phone (spec->params->pipeline), set_parameter (param edit -> regenerate, the reconciliation channel), get_parameters, regenerate (deterministic replay with rollback), validate (P6). NEW geometry verbs the set LACKS: Loft/Sweep/Revolve side-profile and Shell/Thicken (P2, via Unsupported.ModelerOperations.* or stacked-disc), plus curved-face-targeting overloads of AddPocket/Slit/Hole/Boss/HolePattern (P4). All NEW dispatch arms extend the proven switch at LlmToolDispatcher.cs:61+ — NOT duplicated in a parallel Python tool surface.

## Validation layer
Two tiers, both kernel-truth (read the live B-rep, never trust the extractor). TIER 1 pre-generation (PhoneParameters.Validate() + DesignRules): reject impossible specs before any geometry — bump_height<total_thickness, bezel>=min_wall, pocket_depth<T-min_wall, grille_pitch>hole_d, lens-to-island clearance, positive dimensions. TIER 2 post-generation (ValidationService, P6) on the actual solid: (1) closed-solid / single-lump check (Shape.Volume>0, no naked edges) — the most basic manufacturability gate; (2) min-wall-thickness by offset/ray sampling at N points (the thin-shell killer — pocket-floor-to-back, flank thickness); (3) self-intersection / Boolean-failure detection (mod-tool failures currently surface only as swallowed kernel exceptions — make them explicit); (4) feature clearance via ContainsPoint material-side probes between adjacent features (no overlapping holes/slots); (5) draft/face-normal sanity. The oracle methodology is the SAME fingerprint used across the 12-model matrix: analytic-volume vs measured-volume, predicted-vs-actual face count, and ContainsPoint straddle (CylinderRoleClassifier.ProbeSolidCore style) — proven, not new.

## Spec -> params
A SpecParser (P7) turns an NL/spec string into a populated, validated PhoneParameters. The LLM's role is BOUNDED to parsing+defaulting+inference: it extracts explicit values ('146.7x71.5x7.4' -> L/W/T; 'USB-C' -> port{type:usbc, default pos/size}; 'speaker grille' -> grille array with default pitch/count) and INFERS unspecified fields from defaults/presets (corner_r, bezels, min_wall from an iphone-like preset). The LLM does NOT do geometry — it emits a structured PhoneParameters JSON, which then passes through the deterministic Tier-1 Validate() (so an LLM hallucination that violates bump_height<total_thickness is REJECTED with a specific reason, not silently built). This runs over the existing MCP/LlmToolDispatcher loop via the new generate_phone tool — the same proven dispatch surface that already marshals tools/call -> SC API thread, so no parallel Python tool layer is stood up. The LLM is the front-door translator; PhoneParameters + DesignRules are the guardrail.
