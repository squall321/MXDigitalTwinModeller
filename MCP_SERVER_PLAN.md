# MCP SpaceClaim Server — Architecture & Build Plan

(Generated by mcp-spaceclaim-design workflow, 2026-06-23. 5-agent: 3 designs -> judge -> synthesis.)

## Winner
HYBRID: Approach C as the primary interactive path (in-process Add-In HttpListener MCP server, marshalling via Application.ExecuteOnMainThread + WriteBlock.ExecuteTask, single persistent SessionContext holding DesignBody+Graph), with Approach B's fresh-SpaceClaim.exe /RunScript reserved STRICTLY as the poison-recovery / hard-reset fallback when in-session re-import via RealModelPipeline.Run still yields an invalid body. C for speed and session continuity; B's process isolation only when the kernel is truly poisoned.

## Decisive reason
Factor #1 (thread-marshalling — a design that can't marshal is DEAD) is RESOLVED, not assumed: Application.ExecuteOnMainThread(SpaceClaim.Api.V252.Task) is present at SpaceClaim.Api.V252.xml:5501, explicitly documented as working under NewAppDomain (where raw BeginInvoke fails), and Task is the same delegate WriteBlock.ExecuteTask(string,Task) consumes (xml:614). So both C and A can legally run Dispatch on the API thread from a background socket thread. With marshalling alive, factor #2 (interactive latency) becomes decisive, and only C/A keep SC warm to amortize the one-time 60-100s cold start; B re-pays 45-90s EVERY call by design and is therefore disqualified as the interactive default. C beats A purely on factor #5 (one in-process codebase + live single-source tool schemas via LlmToolRegistry.GetAllTools() vs A's dual process + drift-prone static schema export). B is retained only for factor #4's worst case, where the matrix harness's verified kill-and-reimport is the proven recovery."}

## Architecture
Approach C (in-process HttpListener MCP server inside the SpaceClaim Add-In) as the interactive spine, with Approach B (fresh SpaceClaim.exe /RunScript) reserved ONLY as the last-resort poison hard-reset. Verified against the live tree, not assumed:

- Marshalling primitive EXISTS: Application.ExecuteOnMainThread(Task) at SpaceClaim.Api.V252.xml:5501; WriteBlock.ExecuteTask(string,Task) at xml:614 (entire op rolled back on CommandException or user interrupt). Both confirmed present.
- HOST ATTRIBUTE is actually host="SameAppDomain" (MXDigitalTwinModeller.Manifest.xml:7), NOT NewAppDomain. This is the EASIER case: raw BeginInvoke would also work, but we still use ExecuteOnMainThread because it is host-agnostic and removes the GATE-1 caveat entirely. (The verdict assumed NewAppDomain risk; the real manifest makes marshalling lower-risk than the verdict feared.)
- Dispatch entry point confirmed: LlmToolDispatcher.Dispatch(DesignBody, FeatureGraph, string toolName, string inputJson) at line 40, returns a JSON envelope, never throws, and explicitly allows null DesignBody for read-only tools get_feature_graph / find_features_by_type (line 44).
- Tool count is 20, NOT 27 (verdict is stale): grep of `new ToolDef` in LlmToolRegistry.cs = 20; `case "` in LlmToolDispatcher.cs = 20. Plan sizes everything to 20.
- AddIn.Connect()/Initialize() exist (AddIn.cs:148/179) but are currently near-empty stubs — the HttpListener bootstrap drops in cleanly there.

The whole interactive session lives in ONE persistent SpaceClaim.exe; a single static SessionContext holds {DesignBody, FeatureGraph, SourcePath, lastGoodScdocPath}. The MCP CLIENT owns the LLM + API key; the server is pure tool execution, replacing LlmClient.cs's in-process Anthropic loop (LlmClient.cs:182 already calls the identical Dispatch).

## GATE-0 (de-risk FIRST, blocking)
GATE-0 (must PASS before writing any HTTP/socket code; ~1 day). Smallest possible proof that a background thread can mutate the open SpaceClaim document via the documented primitives, under THIS add-in's real manifest host.

Build a throwaway ribbon command `GateMarshalTestCommand` (one button) inside the existing Add-In. On click it does:

1. Capture the API-thread id: int apiThreadId = Thread.CurrentThread.ManagedThreadId; (recorded on click = API thread).
2. Spin up a raw background thread: new Thread(() => { ... }).Start();  — explicitly NOT the API thread, to mimic the future HttpListener callback thread.
3. Inside that bg thread:
   var done = new ManualResetEventSlim(false);
   int ranOnThreadId = -1; bool insideWriteBlock = false; Exception err = null;
   Application.ExecuteOnMainThread(new Task(() => {
       try {
           WriteBlock.ExecuteTask("GATE create body", new Task(() => {
               ranOnThreadId = Thread.CurrentThread.ManagedThreadId;
               insideWriteBlock = WriteBlock.IsActive;
               // real mutation: create a 10mm block in the active part
               Body b = Body.CreateBox(Point.Create(0,0,0), Point.Create(0.01,0.01,0.01));
               DesignBody.Create(Window.ActiveWindow.Document.MainPart, "GateBox", b);
           }));
       } catch (Exception e) { err = e; }
       finally { done.Set(); }
   }));
   bool completed = done.Wait(TimeSpan.FromSeconds(30));
4. Assert ALL of:
   (a) completed == true                      -> ExecuteOnMainThread actually pumped (GATE-2: void/fire-and-forget made synchronous via MRES).
   (b) ranOnThreadId == apiThreadId           -> body ran on the SC API thread, not the bg thread (GATE-1).
   (c) insideWriteBlock == true               -> WriteBlock context valid from a marshalled task.
   (d) a new "GateBox" body is visible in the tree AND survives one Ctrl+Z as a single undo step -> mutation committed + rollback granularity correct.
   (e) THROW test: re-run with the lambda doing `throw new CommandException("x")`; assert err is captured on the bg thread (not swallowed by SC's pump) AND the tree shows NO partial body (GATE-2 exception propagation + rollback).
   (f) HANG test (GATE-3): open the STEP-import modal dialog manually, then click the gate button; assert done.Wait(30s) RETURNS FALSE (times out cleanly) rather than the UI deadlocking — proves bounded-wait is the right contract and modal dialogs are a real hang source to suppress.

PASS criteria: a,b,c,d,e all true and f times out cleanly. If b fails (ran on bg thread) or a hangs with no modal, STOP — the entire Approach-C spine is invalid and we fall back to Approach B (process-per-call). Because the manifest is SameAppDomain, b is expected to pass; f is the one most likely to surface a real design constraint (must suppress modal STEP dialog during load_model).

## Components

- **[C# (in Add-In, throwaway)] GateMarshalTestCommand.cs** — GATE-0 only. Background-thread -> ExecuteOnMainThread -> WriteBlock.ExecuteTask body creation + thread-id/exception/hang assertions. Deleted (or kept disabled) once GATE passes.
- **[C# (in Add-In)] McpHttpServer.cs** — System.Net.HttpListener bound to http://127.0.0.1:<ephemeral>/mcp, loopback only, started in AddIn.Initialize / Connect, torn down on Disconnect + Application.ExitProposed. One listener thread; dispatches each request to a single-in-flight work queue (serialized). Validates Origin header + per-session token.
- **[C# (in Add-In)] McpJsonRpc.cs** — Minimal JSON-RPC 2.0 + MCP handshake: initialize (returns protocolVersion, capabilities{tools:{}}, serverInfo), notifications/initialized, tools/list, tools/call. Hand-rolled JSON to match existing FeatureGraphJsonWriter style (no Newtonsoft dependency added).
- **[C# (in Add-In)] McpToolAdapter.cs** — CRITICAL ADAPTER: maps LlmToolRegistry.GetAllTools() (20 ToolDefs) into MCP tools/list shape. NOTE the field-name fix: registry's ToToolsArrayJson() emits "input_schema" (Anthropic Messages style); MCP requires "inputSchema" (camelCase). This adapter re-emits name+description+inputSchema from the SAME GetAllTools() source so there is ZERO schema drift and ZERO second hand-maintained copy.
- **[C# (in Add-In)] ApiThreadMarshaller.cs** — Wraps the verified primitive: Run<string>(Func<string> work, int timeoutMs) -> ManualResetEventSlim + Application.ExecuteOnMainThread(new Task(()=>{ try{result=work();}catch(e){err=e;}finally{done.Set();} })) + done.Wait(timeout). Read-only tools call work() directly; mutating tools have work() itself open WriteBlock.ExecuteTask. Captures result + exception across the thread boundary. Throws TimeoutException on hang (GATE-3 contract).
- **[C# (in Add-In, static singleton)] SessionContext.cs** — Holds the live interactive session: DesignBody, FeatureGraph, SourcePath, LastGoodScdocPath, Poisoned flag, ToolLog (replayable). open_model tool populates it via RealModelPipeline.Run; after each SUCCESSFUL mutation the graph is re-extracted via FeatureExtractor in the SAME API-thread lambda and a last-good .scdoc snapshot is saved.
- **[C# (in Add-In)] McpToolExecutor.cs** — tools/call handler. Resolves tool name; for read-only -> ApiThreadMarshaller.Run(()=>LlmToolDispatcher.Dispatch(null,session.Graph,name,args)); for mutating -> Run(()=>WriteBlock.ExecuteTask(name,()=>{ env=Dispatch(session.DesignBody,session.Graph,name,args); if success re-extract graph + snapshot; })). Maps Dispatch {success:false} envelopes to MCP isError tool_result. Runs poison probe + recovery ladder on failure.
- **[C# (in Add-In)] open_model meta-tool (added to executor, not registry)** — Session bootstrap tool NOT in the 20 geometry tools: wraps RealModelPipeline.Run(path,outDir) -> populates SessionContext. Surfaced in tools/list as a 21st tool. Suppresses the modal STEP-import dialog during import (GATE-3 mitigation) or runs import on the API thread with dialog auto-dismiss.
- **[Node or Python (separate, ship-only-if-needed)] mcp-stdio-relay (optional, ~30 lines)** — Thin stdio<->HTTP shim for MCP clients that cannot speak Streamable-HTTP. Forwards JSON-RPC bytes verbatim; NO schema knowledge, NO translation — eliminates Approach A's drift risk. Reads the handshake file for port+token.
- **[JSON on disk (e.g. %LOCALAPPDATA%/MXDTM/mcp_handshake.json)] handshake file** — Written by McpHttpServer at startup: {port, token, pid}. The local auth guard (MCP puts auth on client, but the loopback socket still needs a guard) and how the relay/client discovers the ephemeral port.
- **[PowerShell + IronPython (reuse existing Test/RE_SelfTest harness)] ScHardReset.ps1 / process-per-call fallback** — Poison LAST RESORT only. Reuses the proven Cleanup-SC (taskkill /F SpaceClaim.exe + ansyscl) + SpaceClaim.exe /RunScript replay-from-last-good-snapshot path from run_mod_matrix.ps1. Invoked by the executor only when in-session re-import still yields an invalid body.

## Tool surface
REUSE LlmToolRegistry's tool definitions directly as the single source of truth — but the count is 20, not 27 (verdict stale; verified: 20 `new ToolDef` entries, 20 dispatcher `case` arms). The 20: change_wall_thickness, change_hole_diameter, change_fillet_radius, change_boss_diameter, change_boss_height, add_boss, add_hole, add_slit, add_pocket, add_rib, add_chamfer, add_hole_pattern, remove_hole, move_hole, move_boss, rotate_boss, rotate_hole, mirror_feature, get_feature_graph, find_features_by_type.

tools/list is served LIVE from LlmToolRegistry.GetAllTools() via McpToolAdapter — NOT a static export, so it can never drift. THE ONE REQUIRED FIX: the registry's ToToolsArrayJson() emits "input_schema" (Anthropic Messages API field), while MCP tools/list requires "inputSchema" (camelCase). McpToolAdapter re-emits the same ToolDef.InputSchemaJson under the MCP key name. Do NOT reuse ToToolsArrayJson() verbatim for MCP — only GetAllTools().

State flow (the read->write->read interactive loop, all against ONE in-memory body):
1. open_model(path) [21st meta-tool] -> RealModelPipeline.Run -> SessionContext{DesignBody,Graph} populated on API thread; modal STEP dialog suppressed.
2. get_feature_graph -> read-only, null DesignBody allowed (Dispatch line 44), returns FeatureGraphJsonWriter.ToJson(session.Graph). LLM reads IDs (H1, FC1, B1...).
3. change_hole_diameter{hole_id:H1,...} -> mutating: WriteBlock.ExecuteTask -> Dispatch mutates session.DesignBody -> on success, FeatureExtractor RE-EXTRACTS session.Graph in the SAME lambda + snapshots last-good .scdoc.
4. get_feature_graph again -> reflects the edit because step 3 re-extracted.
Dispatch is STATELESS (takes body+graph as params, line 40); SessionContext owns all persistence. find_features_by_type is also read-only. Only the 18 mutating tools take the WriteBlock wrapper.

## Poison recovery
Layered ladder; default path is cheap and non-fatal, full restart only as last resort. Built on the verified fact that WriteBlock.ExecuteTask rolls back the ENTIRE op on CommandException or user interrupt (xml:622).

Layer 0 — never crash on a bad tool: Dispatch already returns {success:false,error:...} instead of throwing (line 40 contract). The WriteBlock try/catch turns any geometry exception into a single rolled-back undo step. A failed tool becomes an MCP isError:true tool_result; the HTTP server, SessionContext, and open document ALL survive. The client LLM simply retries with different params. This handles the majority of failures with zero recovery cost.

Layer 1 — poison detection after a FAILED mutation: run a cheap validity probe on the API thread in the same serialized slot — re-extract the graph (FeatureExtractor) and/or Body.GetMassProperties / body-health check. If the probe throws "object is deleted" or yields an invalid body, mark SessionContext.Poisoned = true. (Crucially: only mutate/snapshot on SUCCESS — a failed op never overwrites LastGoodScdocPath, mirroring the matrix harness's SaveAs-on-success-only discipline.)

Layer 2 — in-session re-import (session survives, ~60-100s, NO process restart): re-run RealModelPipeline.Run(session.LastGoodScdocPath) on the API thread to rebuild a fresh DesignBody into the SAME process. The HTTP server + MCP session object are untouched; only the in-SC document is rebuilt from the most recent good snapshot. Replay the tool log up to the last good state if needed.

Layer 3 — kernel-truth fingerprint AFTER any recovery (MANDATORY, per project memory): the 11752-hole misclassification proved a re-import can "succeed" yet yield a DIFFERENT FeatureGraph, silently breaking feature-ID stability and downstream Named Selections. So after Layer 2, compute the extractor-independent kernel-truth fingerprint and compare to the pre-poison fingerprint. If they diverge, surface a warning to the client (feature IDs may have shifted) rather than silently continuing.

Layer 4 — hard reset (LAST RESORT, Approach B): if Layer 2 re-import STILL yields an invalid body, the executor invokes the proven Cleanup-SC (taskkill /F SpaceClaim.exe + ansyscl) + SpaceClaim.exe /RunScript to relaunch and replay from LastGoodScdocPath + tool log. This reintroduces the matrix harness's fresh-process guarantee as a fallback, never the default. If even this fails, return a hard MCP error telling the client SpaceClaim needs an operator restart.

## Biggest risk
BIGGEST RISK: API-thread starvation / modal-dialog hang during load_model (GATE-3), NOT the marshalling primitive itself. The primitive is verified present (xml:5501/614) and the host is SameAppDomain (the friendly case), so the thread-marshalling 'unknown' the verdict feared is largely de-risked before we start. The real hazard is behavioral: Application.ExecuteOnMainThread queues a Task onto SpaceClaim's WinForms message pump, but that pump STOPS draining when a MODAL dialog is open — and the STEP/scdoc importer is known to raise exactly such a dialog (documented in this project's step_import_hang_investigation). So the very first open_model call can enqueue a Task that never runs, and a naive synchronous done.Wait() would hang the MCP request indefinitely. Secondary edges of the same risk: a user clicking/dragging in the shared GUI mid-mutation can delay the queued Task unboundedly, and SC's pump could swallow an exception thrown inside the lambda if the MRES capture is wired wrong.

EARLY SIGNAL TO WATCH (caught in M0, before any HTTP code exists): GATE-0 assertion (f) — open the STEP-import modal dialog, click the gate button, and watch whether done.Wait(30s) returns FALSE cleanly or the UI deadlocks. If it deadlocks (no clean timeout) OR if assertion (b) shows the body ran on the bg thread, that is the kill signal: the in-process Approach-C spine cannot bound its waits and we must either (1) suppress/auto-dismiss the modal importer and run open_model off the dialog path, or (2) fall back to Approach B (process-per-call /RunScript, which needs no marshalling and no live pump). Watch this in M0; every later milestone assumes a clean bounded timeout under a busy/blocked API thread. The mandatory mitigations baked into the design: STRICT one-call-in-flight serialization, bounded done.Wait with a structured timeout error, and modal-dialog suppression during import.
